# Agent configuration precedence: explicit YAML file outranks ambient environment variables

## Context and Problem Statement

The Helvilette Agent merges configuration from four sources: built-in defaults, a YAML
config file, environment variables, and CLI flags. The README ([`README.md:182`](../../../README.md))
documents the priority as **CLI flags > YAML config > Environment variables > Defaults**,
but `LoadConfig` in [`cmd/agent/main.go:60`](../../../cmd/agent/main.go) applies them in the
order defaults → YAML → env → CLI, which makes environment variables override the config
file — the opposite of the documented behaviour.

This was reported as [issue #9](https://github.com/AlexanderSlokov/Helvilette/issues/9),
alongside [issue #8](https://github.com/AlexanderSlokov/Helvilette/issues/8) (the README's
YAML example uses keys `otherlaUrl`/`nodeId` that the parser does not recognise, so the
example silently yields a default-configured agent).

Which source should win when the YAML file and the environment disagree, and is the fix
in the documentation or in the code?

## Decision Drivers

* **Operator Experience from day-0 to day-n is the overriding priority for the naughtian
  stack.** Helvilette is built for SRE/infra engineers; the cost of diagnosing a
  misconfiguration during an incident outweighs conventional purity.
* Cost of diagnosing a conflict between two configuration sources.
* Consistency with the project's own stated design intent — the README describes the
  config file as tasting "like kubelet".
* Compatibility risk for already-deployed agents, since this changes runtime behaviour.
* Container ergonomics: environment injection must remain a usable override path.

## Considered Options

* **Option A — Change the code**: reorder `LoadConfig` to defaults → env → YAML → CLI, so
  the config file outranks environment variables and the implementation matches the README.
* **Option B — Change the README**: keep the current implementation and correct the
  documented order to CLI > env > YAML > defaults, following the viper/12-factor convention.

## Decision Outcome

Chosen option: **"Option A — Change the code"**, because the failure mode it removes —
invisible ambient state silently overriding an explicit, version-controlled artifact — is
the single most expensive configuration bug to diagnose during an incident, and because
day-0 ergonomics are unaffected by the change.

The decisive argument is the **asymmetry in diagnosis cost** when sources conflict:

| Direction | What the operator experiences | Cost |
|---|---|---|
| env beats file | `agent.yaml` shows the correct `othelaURL`, yet the agent talks to a different control plane. Root cause must be hunted through `systemctl show`, `/proc/<pid>/environ`, `docker inspect`, a shared `EnvironmentFile=`, or a stale `export` | High, with **no signpost pointing at the cause** |
| file beats env | An env override does not take effect. Opening the file reveals the winning value immediately | Low, **self-explanatory** |

Environment variables are ambient: not greppable, not in version control, and inherited by
accident. The YAML file is the explicit artifact that config management pushes and that
review processes gate. Letting ambient state win inverts that governance model, and lets a
config-management tool report "converged" while the node runs different values.

Critically, **CLI flags remain the highest-priority source under both options**, so the
day-0 story — one quick command to bring up the first node — is unchanged. This decision
only affects day-1 through day-n, where file-as-source-of-truth is the correct model.

Environment injection also remains a viable override path for containers: `args:` in a pod
spec are CLI flags, and config files can be mounted.

### Consequences

* Good, because the documented and actual behaviour converge, removing a discrepancy that
  would otherwise surface mid-incident.
* Good, because the explicit, reviewable, version-controlled source of truth is the one
  that wins, aligning configuration precedence with change management.
* Good, because it matches k3s, the closest analogue in the ecosystem (see More Information).
* Bad, because it changes runtime behaviour: any deployment relying on an environment
  variable to override a config file will change control plane after upgrade. This must be
  called out in the CHANGELOG as a breaking change.
* Neutral, because it diverges from the viper/12-factor convention that many Go tools
  follow, which may briefly surprise contributors arriving from that ecosystem.

### Confirmation

* Unit tests in `cmd/agent/main_test.go` asserting the full precedence chain, specifically
  a YAML-vs-env conflict resolving in favour of YAML. Only `TestLoadConfig_CLI_Overrides`
  exists today; the YAML-vs-env ordering is currently untested.
* The README precedence sentence and the worked YAML example are reviewed against
  `LoadConfig` in the same pull request that changes the ordering.

## Pros and Cons of the Options

### Option A — Change the code (chosen)

* Good, because the visible artifact wins over invisible ambient state, which is the
  property that matters most when debugging under pressure.
* Good, because it honours the intent the README already states, rather than lowering the
  documentation to match an unintended implementation detail.
* Good, because it matches k3s behaviour, keeping operators' cross-tool intuition intact.
* Bad, because it is a behavioural change requiring a CHANGELOG entry and a release note.

### Option B — Change the README

* Good, because it carries zero runtime risk and is a one-line edit.
* Good, because it follows viper's precedence (Set > flag > env > config > defaults), the
  most common convention in the Go ecosystem.
* Bad, because it preserves the expensive-to-diagnose failure mode described above.
* Bad, because it contradicts the project's stated "taste like kubelet" design direction.

## More Information

**Ecosystem survey.** The intuition that environment variables always outrank YAML comes
from viper and 12-factor, not from the Kubernetes ecosystem:

| Tool | Order | env vs file |
|---|---|---|
| k3s | CLI > config file > env > defaults | **file wins** |
| kubelet | CLI > config file > defaults | no env layer at all |
| kubectl | `--kubeconfig` > `KUBECONFIG` > `~/.kube/config` | env only *locates* the file; it does not override values inside it |
| viper | Set > flag > env > config > defaults | **env wins** |

**On the k3s evidence.** The [k3s documentation](https://docs.k3s.io/installation/configuration)
states only that "CLI arguments will take precedence" over the config file; it does **not**
document env vs config file. The ordering above was therefore derived from the
implementation: [`pkg/configfilearg/parser.go`](https://github.com/k3s-io/k3s/blob/master/pkg/configfilearg/parser.go)
does not unmarshal YAML into a struct — it converts each config entry into a CLI argument
(`--key=value`) and injects those *before* the user's own arguments. Because config values
thereby become genuine command-line arguments, and because urfave/cli treats `EnvVar` only
as a flag's *default value*, explicitly-passed arguments override the environment. Hence
k3s resolves to CLI > config file > env > defaults.

Caveat: several `K3S_*` variables (`K3S_TOKEN`, `K3S_URL`, `INSTALL_K3S_*`) are consumed by
the install script or read via `os.Getenv` outside urfave/cli, so this rule does not hold
uniformly for every k3s environment variable.

**Scope of the implementing pull request.** Issues #8 and #9 touch the same README section
and the same function, and are fixed together:

1. Reorder `LoadConfig` to defaults → env → YAML → CLI.
2. Adopt strict YAML decoding (`yaml.NewDecoder` + `KnownFields(true)`) so an unrecognised
   key fails at startup instead of silently falling back to defaults — the root cause of
   issue #8's silent failure.
3. Correct the README example keys to `othelaURL`/`nodeID` and add the missing
   `workspaceDir`.
4. Add precedence tests, and a CHANGELOG entry recording the breaking change.

**Deferred, tracked separately.** Two operator-experience improvements were identified
during this discussion but fall outside the scope of issues #8 and #9:

* **Startup provenance logging** — log the resolved configuration with the source of each
  value (`source=config-file`, `source=env(NODE_ID)`, `source=default`). This largely
  neutralises the precedence question in practice, since operators no longer need to recall
  the ordering to explain what a node is doing.
* **`NodeID` default** — `DefaultConfig` returns `"agent-01"` (`cmd/agent/main.go:41`), a
  fleet-colliding default that amplified issue #8 from a single misconfigured node into
  every node registering under the same identity. Defaulting to `os.Hostname()`, or
  requiring the value outright, contains that blast radius.

**Revisit if** Helvilette gains a drop-in config directory (k3s-style `config.yaml.d/`), or
if container-first deployment becomes the dominant installation mode and environment
injection proves to be the primary override path in practice.
