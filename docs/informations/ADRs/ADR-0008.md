# The agent stands alone; Othela is optional and frozen

The direction comes from two documents written by the project owner on
2026-10-11: the design doctrine
([Software Design Doctrine Follow the Soviet's Weapons](../../references/Software%20Design%20Doctrine%20Follow%20the%20Soviet's%20Weapons.md))
and the roadmap built on it
([Helvilette_revedict](../../references/Helvilette_revedict.md)). This record
takes the decisions those documents imply for the code. It also records the
places where the owner chose differently from the roadmap text. The decisions
are D1 to D9.

## Context and Problem Statement

### What the agent depends on today

The agent cannot do anything without Othela:

- `RegisterNode` retries in an unbounded loop (`cmd/agent/agent.go:58`), and
  `Run` calls it before anything else. Othela down means no node reconciles.
- Work arrives only through `Poll` (`GET /sync/<node>`), and results leave only
  through `SendReport`. The agent never reads `helvilette.yml` itself; Othela
  reads it and hands out a `types.Job`.
- The default workspace is `/tmp/helvilette` (`cmd/agent/config.go:76`), so the
  on-disk record that detects an interrupted run can vanish on reboot.
- `ExecutePlaybook` applies directly, with no check run first
  (`cmd/agent/executor.go:92`).

The full list is issue #43.

### What the doctrine asks for

Law 0: if it fires in peacetime, it must fire under fire. Software has two
states: it runs as declared, or it refuses and says why. "Runs but wrong" is
the operator's main enemy.

The doctrine uses the MiG-21 as its picture: a simple aircraft that relies on
ground radar, but still flies when the link is lost. Today the agent is the
opposite. Lose the ground station and it stays on the runway.

The doctrine also records its own early mistake: forcing one shape on every
tool because the author admired that shape. Helvilette's first shape was copied
from Kubernetes (control plane, agents, SQLite) and became too heavy for the
author to run in their own homelab. The desired state already lives in git, so
a server that holds a second copy of it is a second source of truth.

### What the roadmap asks for

Phase 0 separates the agent from Othela and scouts `ansible-pull`. Phase 1
ships Agent 1.0, an `ansible-pull` that is upgraded with care. Phase 2 is a
public beta. Phase 3 resumes Othela, and only when a real team needs
multi-node coordination.

## Decision

### D1. The agent runs without Othela

The agent reads its desired state from its own git checkout. Its only network
dependencies are the git server and, for tasks that need secrets, Kallisto.
`RegisterNode`, `Poll` and `SendReport` leave the agent's run path. The agent
has no "Othela mode".

The invariant for Phase 3 is the one the roadmap states. Othela only reads the
records agents write, and only writes to git. Remove Othela and every agent
keeps running as before.

### D2. Do what `ansible-pull` does

Helvilette does not reinvent the pull model. Like `ansible-pull -U <url> -C
<branch>`, the repository URL and branch belong to the node's local
configuration (`agent.yaml`, flags or environment, layered as in ADR-0001),
usually set by cloud-init. Every pull-based tool needs this one value per
node, so it is not a burden Helvilette adds.

Playbook selection:

1. If the repository has `helvilette.yml` at its root, it maps node labels to
   playbooks and says which playbooks may apply automatically and which only
   plan.
2. Otherwise, use `ansible-pull`'s convention: `<fqdn>.yml`, then
   `<hostname>.yml`, then `local.yml`.

Left open until the Phase 0 scouting: does the agent call `ansible-pull` as its
engine, or only follow its design? The scouting table decides each feature as
reuse, wrap or write.

### D3. The manifest stays `helvilette.yml`

Every other YAML file in the project uses `.yml`. ADR-0006's warning on
`helvilette.yaml` as a near miss stays.

`spec.repo` loses its purpose: the manifest now sits in the repository it would
point to. This supersedes the fleet-repository and playbook-repository split
from ADR-0003 for the agent path. The new schema is decided in its own ADR.
`v1alpha1` is still alpha, so breaking changes are allowed until v1. From v1
on, the manifest and the run record only gain fields.

### D4. The agent is a long-running daemon

The roadmap text says "no long-running process". That rule depends on the tool.
Helvilette's job includes health probes and remediation (D7), which need
continuous watching, so Helvilette is allowed a daemon. The doctrine's own
first principle is mission first, shape second.

The daemon must still survive harsh handling (doctrine, "Bổ sung" 1):

- Every state that matters lives on disk. Memory holds only what can be
  rebuilt.
- State files are written atomically: write a temp file, then rename.
- `kill -9` at any instruction is safe. The next start detects the interrupted
  run.
- systemd restarts it (`Restart=always`). The agent does not supervise itself.
- Nothing lives in `/tmp`. The workspace defaults to
  `/var/lib/helvilette/agent`.

### D5. An interrupted run is re-run from the start

If the agent finds a run that never finished (crash, `kill -9`, power loss), it
writes that into the run record and runs the commit again from the beginning.
Nothing happens silently, because the interruption is on record.

This supersedes backlog 3.10, "at-most-once, never silently retry". Re-running
relies on idempotent playbooks. The documentation tells operators to test their
roles with Molecule before giving Helvilette auto-apply.

### D6. Ansible is the ammunition, and it is pinned

The doctrine treats Ansible as ammunition: required by the mission, so it must
be pinned and packaged. Helvilette ships a pinned Ansible with the agent.
Operators who already manage Ansible can provide the dependencies themselves,
as long as they meet the pinned version. Every run record carries the Ansible
version that ran.

### D7. Probes and remediation are core, and opt-in

Health probes (liveness for systemd services) and remediation playbooks are
core features. They are not "acting behind the operator's back", because each
one is enabled per service in `helvilette.yml`, with a reason. That file is
signed (D9), so the permission is on record.

- Every remediation run is written to the run record and the journal.
- A failing remediation backs off; it does not loop.
- The agent never lifts a halt by itself, and never reverses an operator's
  decision.

Gate conditions for rolling updates are not agent work. They move to Othela
(D8).

### D8. Othela stays in the tree, frozen

`cmd/othela`, `pkg/storage` and the fleet sync code stay in the repository, but
their development stops. README and BACKLOG say Helvilette is under overhaul and
that the agent is completed first.

Rolling updates and other multi-node deployment strategies are Othela's job.
They resume in Phase 3, when a real team with a real need for multi-node
coordination exists. The graduation test for that phase is k3s-ansible on a
fleet, plus a Concorde test for Othela.

### D9. Check first, signed commits, no `apply`

- Every cycle runs `ansible-playbook --check --diff` before anything else. If
  the check fails, the agent stops and the node keeps its previous state.
- Only commits signed by a key in the agent's local configuration are accepted.
  Anyone who can push to the repository can grant auto-apply, so this check is
  the only lock on that door.
- There is no `helvilette apply`. The rescue tool is `ansible-playbook`, which
  the operator already has. A playbook in a Helvilette repository stays a plain
  playbook.

## Consequences

### Positive

- One node with one git repository is a complete deployment. The homelab test
  becomes possible.
- The open questions in issues #22 and #23 (observed state versus desired state)
  shrink to one machine: desired state is the last verified commit, and
  observed state is the last check result on disk.
- Most of the hardening work lands where the doctrine says to put the extra
  care: the agent, which runs on every machine.

### Negative and breaking

- The agent's `--othela-url` flag and its default lose their meaning. The agent
  unit and the e2e topology change: the e2e stack no longer needs an Othela
  node to prove the agent works.
- ADR-0003's `spec.repo` and the fleet-repository model no longer describe the
  agent path. ADR-0005's fleet sync becomes Othela-only, and frozen with it.
- Backlog 3.10 (at-most-once) is reversed by D5.
- The e2e suite in `tests/e2e/gitops_test.go` asserts the Othela dispatch path,
  so it has to be rewritten for the standalone agent.

### Neutral

- ADR-0001 (configuration precedence and `--print-config`) carries over, and
  becomes the base for `helvilette config`.
- ADR-0004 (no identical `nodeSelector` maps) still applies, now checked by the
  agent.
- ADR-0006 (every skipped path logs) and ADR-0007 (journald fields, the
  systemd-in-container fleet) carry over unchanged.
