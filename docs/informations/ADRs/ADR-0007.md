# Replace the Vagrant manual-test environment with a systemd-in-container fleet

Requirements were dictated by the project owner and are recorded below as R1 to
R3; the decisions taken against them are D1 to D5.

## Context and Problem Statement

The Vagrant environment under `vagrant/` is unreliable as a test bed for
Helvilette. The decision to rebuild rather than repair is recorded in BACKLOG
section 8. Two distinct complaints drive it, and they are not the same kind of
problem.

### Complaint 1: Helvilette is hard to find inside a running OS

Answering "did my push reach the agent?" costs three screens with nothing
connecting them:

| Screen | Path | Shows |
| --- | --- | --- |
| 1 | `make othela` then `sudo journalctl -u othela -f` | control plane |
| 2 | `make agent` then `sudo journalctl -u helvi-agent -f` | agent |
| 3 | browser at `192.168.121.10:3000` | Gitea |

Correlation is done by eye, against wall-clock time. Contributing causes:

- Unit names share no prefix: `othela.service` versus `helvi-agent.service`.
  There is no `journalctl -u 'helvi*'` that catches both, and no
  `helvilette.target`.
- There is no aggregation point. Helvilette emits structured JSON, but
  structured JSON is only worth the cost when something collects it. Logs sit in
  two separate journald instances on two separate machines.
- There is no CLI. `h8e status` is still in the backlog. The only way to ask for
  fleet state is `curl .../api/v1/nodes`, which requires knowing the endpoint
  exists and being on the private network.

This is a gap in Helvilette, not in Vagrant. Docker Compose hid it, because
`docker compose logs -f` merges every service into one stream for free. On real
machines — bare metal, edge, scattered VMs, which is Helvilette's target — no
such thing exists. Rebuilding the environment without addressing this would hide
the finding again.

### Complaint 2: the environment is unreliable in a way that cannot be named

The mechanism: **the virtual machines never build Helvilette.** They run a stale
binary from the host.

```yaml
- name: Build Helvilette binaries
  command: make build
  args:
    chdir: /vagrant
    creates: /vagrant/bin/othela    # skipped when the file already exists
```

`/vagrant` is an rsync of the host repository. Vagrant's rsync excludes only
`.vagrant/`; it does not read `.gitignore`. `bin/` is gitignored but is synced
anyway, so `creates:` finds the file and skips the build. The host's `bin/` was
last written 2026-09-08, three weeks before this was written and older than
every fix since.

Consequences that follow from it:

- What is under test depends on what the host happens to have in `bin/`, not on
  anything in the repository. Nothing reports which build is running.
- `make build` sets `CGO_ENABLED=1` for SQLite, so the binary carries the host's
  glibc requirement into a Debian guest. Version skew fails or passes depending
  on the host, and looks random.
- The build branch that is skipped could not have worked anyway: the playbook
  installs `golang-go` from Debian bookworm apt, which is far below the
  `go 1.25.6` that `go.mod` requires. The environment only ever survived by
  skipping the build. It has never stood on its own.

Three further reproducibility defects:

1. **Boot order guarantees a broken first run.** Play 2 starts Othela pointed at
   `.../helvi-test/baseline.git`. Gitea is not installed until play 4, and the
   repository does not exist until a human registers a user in the web UI and
   creates it by hand.
2. **The fixture is not version-controlled.** `vagrant/baseline-repo/` is
   gitignored, so two runs on two machines are not necessarily running the same
   manifest.
3. **`make repo` is not idempotent.** It runs `git init` in a directory that
   already has `.git`, then `git remote add origin`, which fails on the second
   run.

Minor drift in the same file: `/var/lib/helvilette/playbooks` is still created
although ADR-0003 removed `--playbook-dir`, and the `Start Gitea` task appears
twice.

The common root is that the environment has no reproducible starting state.
Four separate dependencies on host condition: prebuilt binaries via rsync,
manual Gitea bootstrap, a gitignored fixture, and a provisioning order that
cannot succeed on first boot.

## Requirements

Dictated by the project owner. Recorded as received; wording is the author's.

### R1. Helvilette logs somewhere a collector already looks

Alloy and Netdata sit **beside** Helvilette. Helvilette does not ship them, does
not manage them, and does not depend on them. This is not a product feature.

What Helvilette owes them is to be well-behaved: put its logs somewhere those
collectors already read, so nobody has to hand a collector an explicit path.
The requirement is the absence of configuration, not the presence of a shipper.

That rules out one thing in particular: **Helvilette must never write to a log
file of its own.** A private path under `/var/log/helvilette/` would have to be
declared to every collector on every node. journald is the destination that
needs no declaration — it is what Alloy's node integration and Netdata's
`systemd-journal` plugin read the moment they are installed.

Where Helvilette already stands: both binaries write JSON to stdout, and under
systemd stdout goes to journald. So the logs are already collected. The gap is
what they look like once there.

Two ways to close it, and the choice is open:

| | JSON on stdout (today) | Native journal fields |
| --- | --- | --- |
| Where fields live | one opaque `MESSAGE` string | real journal fields |
| `journalctl NODE_ID=agent-1` | does not work | works |
| Alloy config needed | a `json` parse stage | relabel rules only |
| Behaviour outside systemd | unchanged, still JSON on stdout | needs a fallback path |
| Code change | none | a journald writer behind `pkg/log` |

The owner leans toward emitting into journald properly, and it is the option
worth costing out: `journalctl NODE_ID=agent-1` answers "what happened on that
node" without knowing a unit name, a file path or a collector. That is a direct
answer to complaint 1 on a real machine, not only in the lab.

One cheap piece belongs here whichever way that goes: a consistent
`SYSLOG_IDENTIFIER` on both binaries. With it, `journalctl -t 'helvilette*'`
selects the whole product without knowing how the units were named. Renaming the
units to a shared prefix — `helvilette-othela.service`, `helvilette-agent.service`
— makes `journalctl -u 'helvilette-*'` work as well, and costs nothing but the
rename.

### R2. Two environments that feel like two complete operating systems

The requirement is the feeling of two full operating systems, not two full
virtual machines.

Base image, confirmed: **`geerlingguy/docker-ubuntu2404-ansible`** — the image
family Molecule uses to test Ansible roles.

What it gives, from its Dockerfile:

- `ubuntu:24.04`, with `CMD ["/lib/systemd/systemd"]`. systemd is PID 1, so
  `systemctl` is real, not a shim.
- `VOLUME ["/sys/fs/cgroup", "/tmp", "/run"]`. The compose file must supply these;
  systemd will not come up otherwise.
- Ansible preinstalled via pip, plus `build-essential`, `python3-dev`, `rsyslog`
  and `systemd-cron`.
- udev and getty units stripped, to keep idle CPU down in a container.

Rationale given: this replicates a real Helvilette runtime 1:1, with a working
`systemctl`, so the control plane and the agent run as services rather than as
foreground processes. This matters because Helvilette's whole premise is that it
lives at the systemd layer. An environment without real systemd cannot exercise
it, and cannot exercise R1 either — journald is a systemd service.

Ansible already being in the image also removes a provisioning step the Vagrant
setup spent an apt round-trip on.

### R3. A pre-baked Git server with real playbooks

A body of real Ansible playbooks, already committed, inside something that
behaves like a Git server. Fidelity of the server is not the point; behaving
like one is.

Acceptance: bring the compose stack up, and the Agent clones the repository.
Nothing else.

**Authentication is out of scope.** The repository is public and cloned
anonymously. Token handling — simulating a GitHub or GitLab API token, and the
credential support in Helvilette that would need to exist for private
repositories — moves to the backlog. Getting the public path working comes
first.

What this requirement does fix, from complaint 2:

- The repository is seeded at image build time, so no human registers a user in
  a web UI and creates a repository by hand. The manual-bootstrap dependency is
  gone.
- The playbooks are tracked in this repository, so two runs on two machines run
  the same fixture. The gitignored-fixture dependency is gone.

## Decision

### D1. Vagrant is deleted

`vagrant/` goes. The manual-test environment is rebuilt as a Docker Compose
stack of systemd-in-container nodes per R2.

`docker-compose.e2e.yaml` is renamed `e2e.compose.yml`.

The two logbooks under `vagrant/docs/` are evidence, not environment: they are
what produced issues #32, #33 and #34, and ADR-0005, ADR-0006 and this ADR all
cite them. They move to `docs/references/logbooks/` rather than being deleted
with the rest.

### D2. Helvilette emits into journald

Settled, and it is the second column of the R1 table, not the first: a journald
writer behind `pkg/log`, emitting real journal fields rather than a JSON blob in
`MESSAGE`. Raised in priority in the backlog.

Behaviour outside systemd stays what it is today — JSON on stdout — so Docker
Compose, `make run-othela` and `go test` are unaffected. The journald sink is
selected when a journal socket is present, not by a flag: a flag would be one
more thing an operator has to know, which is the opposite of what R1 asks for.

`SYSLOG_IDENTIFIER` is set on both binaries, and units are renamed to a shared
prefix, so `journalctl -t 'helvilette*'` and `journalctl -u 'helvilette-*'` both
select the whole product.

### D3. Repository layout

Approved. See "Layout" below.

### D4. Fixtures are baked into the git server image

The playbook repositories are committed into the git server image at build time,
by its Dockerfile. Not bind-mounted, not seeded by a container entrypoint, not
created by a human in a web UI.

What this buys:

- The long inline `sh -c 'mkdir && cp && git init && git add && git commit && exec git daemon'`
  command disappears. It exists twice today, once in the compose file and once in
  `tests/e2e/gitops_test.go`, and the two must stay in step by hand.
- The served commit SHA is fixed at image build time, so every run starts from
  the same commit.
- Nothing writes into the source tree at runtime. The root-owned leftovers that
  `make clean-e2e` exists to remove, and that once broke `go vet ./...`, have no
  way to appear.
- The Ginkgo suite and the Compose stack consume the same image, so they cannot
  disagree about what the repository contains.

Tests that need a *second* commit — the #32 regression path, where a manifest
pushed after startup must be picked up — commit inside the running container.
The image ships a helper script for it so the Ginkgo suite and a human at a
terminal use the same one.

### D5. The plain container images are kept, under build/, and CI builds them

`Dockerfile.othela` and `Dockerfile.agent` built foreground-process containers
and had no consumer but the e2e stack, which the systemd node images replace.
Deleting them was proposed and rejected: Othela, unlike the Agent, has no
systemd dependency, so a foreground container is the correct way to run the
control plane under Docker or Kubernetes.

They move to `build/othela/Dockerfile` and `build/agent/Dockerfile`, separated
from the test images, and `make images` builds both.

**CI runs `make images` as its own job.** Without it these two images have no
consumer at all, and an image nothing builds stops being buildable without
anyone noticing. That is precisely how the Vagrant environment died: its build
path could not have worked for weeks, and nothing exercised it.

## Layout and rationale

The shape D3 approves, and why each part of it is that shape.

### The problem to solve first

The stack is defined twice. `docker-compose.e2e.yaml` and
`tests/e2e/gitops_test.go` each declare the same four services, the same git
daemon bootstrap shell command, the same image builds and the same wait
strategies. They have to be edited in pairs and nothing enforces it. Issue #33
is what that looks like when it fails: the compose file named a flag the binary
did not have, and nothing noticed.

So the layout question is really a single-source-of-truth question. The answer
adopted below: **`e2e.compose.yml` is the definition of the stack, and the
Ginkgo suite drives that file rather than restating it.**

### The tree

```
e2e.compose.yml                  the stack, and the only definition of it
tests/
  e2e/
    e2e_suite_test.go            Ginkgo entry point, unchanged
    gitops_test.go               brings up e2e.compose.yml, then asserts
  images/
    node/
      Dockerfile                 one file, four stages (see below)
      helvilette-othela.service
      helvilette-agent.service
    gitserver/
      Dockerfile                 git daemon, repositories baked in
      seed-commit.sh             adds a commit to a served repo, for #32 tests
  fixtures/
    nginx-collection/            moved from tests/e2e/data/playbooks/
    baseline/                    recovered from vagrant/baseline-repo/, now tracked
docs/references/logbooks/
  FirstLight.md                  moved from vagrant/docs/
  Debugging.md                   moved from vagrant/docs/
```

Removed: `vagrant/`, `Dockerfile.othela`, `Dockerfile.agent`,
`Dockerfile.gitserver`, `docker-compose.e2e.yaml`, `tests/e2e/data/`, and the
`data/agent-*` bind mounts.

Build context is the repository root for every image, so the Go builder stage
can see `go.mod`. Dockerfiles are addressed by path from there.

### One Dockerfile for both node images

`tests/images/node/Dockerfile` has four stages:

```
FROM golang:1.25.6              AS builder      both binaries, CGO_ENABLED=1
FROM geerlingguy/docker-ubuntu2404-ansible AS node-base   systemd, journald config
FROM node-base                  AS othela-node  othela binary + unit, enabled
FROM node-base                  AS agent-node   agent binary + unit, enabled
```

Compose selects a stage with `target:`. This keeps the builder and the base in
one place — no duplicated builder boilerplate, and no ordering problem from a
separately built base image that Compose would not know to build first. Docker's
layer cache shares `builder` and `node-base` between the two.

`node-base` is where the systemd bits that both nodes need live: the cgroup and
`/run` expectations from the upstream image, and the journald configuration that
D2 needs in order to be testable at all.

### Ginkgo drives Compose, not its own topology

Two ways to do it:

1. **Shell out to `docker compose`** from the suite: `up -d --wait`, assert,
   `down -v`. No new dependency, and the suite exercises the same binary and the
   same file a human uses, which is the point.
2. **`testcontainers-go/modules/compose`**, a separate Go module that embeds
   docker/compose as a library.

Option 1 is proposed. Option 2 adds a large dependency tree to reimplement what
`docker compose up --wait` already does, and a Go reimplementation can diverge
from the CLI — which is precisely the class of drift this layout exists to
remove. Readiness comes from `healthcheck` blocks in the compose file, so it is
declared once and honoured by both paths.

### What each change buys

| Change | Removes |
| --- | --- |
| One compose file, Ginkgo drives it | The duplicated topology that let issue #33 ship |
| Fixtures baked into the git server image | The twice-written git bootstrap shell command, and the manual Gitea bootstrap |
| Fixtures tracked in `tests/fixtures/` | The gitignored fixture, so two machines run the same manifest |
| No bind mounts into the source tree | The root-owned leftovers `make clean-e2e` exists to delete |
| systemd nodes | Foreground processes standing in for services; makes D2 testable |

## Consequences

### Positive

- The stack has one definition. `make up` and `make e2e` run the same
  `e2e.compose.yml`, so they cannot disagree the way the compose file and the
  Ginkgo suite did when issue #33 shipped.
- The starting state is reproducible. Nothing depends on what the host happens to
  have in `bin/`, no human clicks through a web UI to create a repository, and
  the fixtures are tracked in `tests/fixtures/`.
- Othela and the Agent run as systemd units under systemd as PID 1, which is the
  layer Helvilette manages. The fixtures can therefore manage real services:
  `baseline` starts chrony, `nginx-collection` starts nginx. Neither worked in a
  foreground-process container.
- journald is a real service in the stack, so R1 and D2 are testable. The suite
  asserts that `journalctl -t helvilette-othela` returns Helvilette's structured
  logs, which is the same path a collector takes.
- Fleet and playbook repositories are separate, as ADR-0003 intended. The
  previous fixture used one repository for both, so the separation was never
  exercised and the loader's recursive scan never saw more than one manifest.
- Nothing writes into the source tree, so `make clean-e2e` no longer has to
  borrow a container's root to delete root-owned directories, and the
  `.gitignore` entries that existed for them are gone.
- The e2e suite builds the stack once for the whole run instead of once per spec.

### Negative

- The node images are large: an Ubuntu userland with Ansible preinstalled, versus
  a Debian slim image with one binary. Cold builds are slower.
- systemd in a container needs `cgroup: host`, a writable `/sys/fs/cgroup`,
  tmpfs on `/run`, `CAP_SYS_ADMIN`, and `SIGRTMIN+3` as the stop signal. That is
  five requirements a reader has to take on faith, which is why they are grouped
  into one commented anchor in the compose file rather than repeated per service.
- The stack depends on a cgroup v2 host. CI asserts this before running, so the
  failure is one line rather than an unexplained systemd boot loop.
- `CAP_SYS_TIME` is granted so the baseline playbook can start chrony. It is a
  real capability handed to a test container; the alternative was a fixture that
  manages a service chosen for being easy rather than for being representative.

### Neutral

- Per-node configuration is one `AGENT_LABELS` line in a mounted env file. systemd
  does not pass the container's environment to the units it starts, so container
  `environment:` blocks would have been silently ignored. Node identity needs no
  configuration at all: the Agent defaults its node-id to the hostname, and
  Compose sets that.
- The three logbooks move to `docs/references/logbooks/`. They are the evidence
  behind issues #32, #33 and #34 and are cited by ADR-0005, ADR-0006 and this
  ADR, so they outlive the environment that produced them.
