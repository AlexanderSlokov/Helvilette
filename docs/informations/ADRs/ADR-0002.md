# Manifest schema identity: `helvilette.io/v1alpha1` with `kind: PlaybookDeployment`, validated on load

## Context and Problem Statement

[Issue #1](https://github.com/AlexanderSlokov/Helvilette/issues/1) (February 2026) proposed the
shape of Helvilette's declarative manifest: two files, `helvilette.configMap.yaml` and
`helvilette.secrets.yml`, carrying `apiVersion: helvilette.io/v1`, `kind: Blueprint`, and three
sections named `inputs`, `roles` and `runtime`.

The implementation that landed five months later in commit `15c181c` went a different way: a
single `helvilette.yml`, `apiVersion: apps/v1`, `kind: Cluster`, and a spec built from
`repo`/`branch`/`playbook`/`nodeGroups`. Hardening and resource limits, which issue #1 wanted to
express declaratively under `runtime.security`, are instead passed through `extra_vars` for
Ansible roles to render. Nothing recorded that divergence, leaving issue #1 readable as if it were
the spec.

Worse, three spellings of the schema identity accumulated in the repository at once:

| Location | apiVersion | kind |
|---|---|---|
| `tests/e2e/data/playbooks/nginx-collection/helvilette.yml` | `apps/v1` | `Cluster` |
| `pkg/manifest/parser_test.go` | `v1` | `Helvilette` |
| Issue #1 | `helvilette.io/v1` | `Blueprint` |

They coexisted because **nothing read either field.** `Manifest.APIVersion` was declared in
`pkg/manifest/types.go` and never referenced anywhere else in the codebase, and `ParseFile` called
`yaml.Unmarshal` with no validation at all.

Two questions follow. Which schema identity is correct, and what should the parser do when a
manifest does not carry it?

## Decision Drivers

* **Operator Experience from day-0 to day-n is the overriding priority for the naughtian stack.**
  The cost of diagnosing a misconfiguration under pressure outweighs conventional purity.
* Correctness against Kubernetes API group conventions, which the project deliberately imitates
  and advertises in the README as a selling point ("K8s-familiar configuration").
* Honesty of the stability promise a version number makes, given that `spec.vault` and
  `nodeGroups[].probes` appear in example manifests but are not yet parsed.
* Compatibility risk, bounded here because the project is pre-release.

## Considered Options

* **Option A — `helvilette.io/v1alpha1` + `kind: PlaybookDeployment`**: own API group, alpha
  stability level, kind renamed to name the object the file actually declares.
* **Option B — keep `apps/v1` + `kind: Cluster`**: change only the test to match the manifests.
* **Option C — `helvilette.io/v1` + `kind: Cluster`**: fix the group, keep the GA version and the
  existing kind.

## Decision Outcome

Chosen option: **"Option A"**, because it is the only option that is correct under the very
conventions the project claims to follow, and because the alpha level states a stability promise
the schema can actually keep today.

**On the group.** Kubernetes API conventions require an API group to be a DNS subdomain that the
project owns. The short, domain-less groups — `apps`, `batch`, `policy`, `autoscaling` — are
historical holdovers from Kubernetes 1.x, retained for compatibility and explicitly not a pattern
for new groups; `.k8s.io` is reserved for Kubernetes itself. `apps/v1` is also an occupied in-tree
group: Deployment, StatefulSet, DaemonSet and ReplicaSet live there. Putting `kind: Cluster` into
it means borrowing another project's namespace for a kind that is not theirs.

k3s settles the question, because it is the closest analogue and had every excuse to do otherwise.
It is a Kubernetes distribution, so it could plausibly file its own kinds under a core group — and
it does not. Every k3s-owned kind sits under a Rancher-owned domain: `k3s.cattle.io/v1` for
`Addon` and `ETCDSnapshotFile`, `helm.cattle.io/v1` for `HelmChart` and `HelmChartConfig`. The
same holds across the ecosystem: Flux uses `*.toolkit.fluxcd.io`, Argo CD `argoproj.io`,
cert-manager `cert-manager.io`, Prometheus Operator `monitoring.coreos.com`.

**On the version.** In Kubernetes the alpha/beta/GA suffix is a contract, not a counter: `v1`
promises backward compatibility for the lifetime of v1. Helvilette cannot honour that promise
while `spec.vault` and `nodeGroups[].probes` sit in shipped example manifests without a parser
behind them, and while the schema has already been rewritten once relative to issue #1.
`v1alpha1` states the true situation and leaves room to land those two sections.

**On the kind.** `kind` names the object the manifest declares. `helvilette.yml` lives inside a
playbook repository and declares which playbook is deployed to which node groups with which
variables. That is not a cluster — in Cluster API, `cluster.x-k8s.io/v1beta1` `kind: Cluster`
means an actual cluster resource. `PlaybookDeployment` names what the file does, and pays the
compatibility cost in the same breaking change as the group rename rather than in a second one.

**On validation.** Fixing the identity is worthless if nothing enforces it, and the underlying
failure is worse than a naming inconsistency. A manifest with a stale `apiVersion`, or with
`nodegroups` misspelled, unmarshalled cleanly into a zero-value `Manifest`. `MatchNodeGroups` then
returned zero matches, `handleSync` fell through, and every agent received `204 No Content` —
with no error, no warning, and no log line anywhere pointing at the file. This is the same class
of defect as issues [#8](https://github.com/AlexanderSlokov/Helvilette/issues/8) and
[#9](https://github.com/AlexanderSlokov/Helvilette/issues/9), one layer up: a configuration file
that looks right, is read successfully, and does nothing.

`ParseFile` therefore validates before returning. `apiVersion` and `kind` must match exactly, and
`metadata.name`, `spec.repo`, `spec.playbook` and a non-empty `spec.nodeGroups` are required, as
is a non-empty `nodeSelector` on each group — an empty selector matches no node, which reads to an
operator as "matches everything" but behaves as the opposite.

### Consequences

* Good, because a manifest that parses is now a manifest that can dispatch. The silent-204 failure
  mode is removed at its source.
* Good, because every rejection names the offending field, its value, and the expected shape, so
  the file can be fixed without reading the parser.
* Good, because the schema identity is now singular and enforced, instead of three spellings none
  of which was checked.
* Good, because `v1alpha1` gives `spec.vault` and `nodeGroups[].probes` room to land without
  breaking a compatibility promise.
* Bad, because it is a breaking change: every existing `helvilette.yml` must update `apiVersion`
  and `kind` or be rejected at load. Acceptable because the project is pre-release, and rejection
  is loud and self-explanatory rather than silent.
* Bad, because `spec.repo` is now required, which makes the `HELV_TEST_REPO_URL` fallback in
  `cmd/othela/server.go` unreachable for manifest-sourced jobs. Left in place for now, to be
  removed separately.
* Neutral, because validation is field-presence only. Unknown keys are still accepted silently,
  so a misspelled key inside `ansible:` or a typo in `probes:` is not yet caught.

### Confirmation

* `pkg/manifest/validation_test.go` covers every rejection path and asserts that messages name the
  expected shape.
* `TestParseFileRejectsSilentlyEmptyManifest` in `pkg/manifest/parser_test.go` is the regression
  test for the failure this ADR describes, including the stale-`apps/v1` and misspelled-
  `nodegroups` cases.
* `TestParseFileMissingFileStaysDetectableAsNotExist` pins the contract `pkg/playbook`'s loader
  depends on to tell "no manifest here" apart from "broken manifest".

## Pros and Cons of the Options

### Option A — `helvilette.io/v1alpha1` + `PlaybookDeployment` (chosen)

* Good, because it follows the convention k3s and the wider ecosystem actually apply to their own
  kinds.
* Good, because the version level is honest about what the schema guarantees today.
* Good, because it spends the breaking change once, covering group, version and kind together.
* Bad, because it invalidates every existing manifest.

### Option B — keep `apps/v1` + `Cluster`

* Good, because it touches no YAML file and carries no compatibility cost.
* Bad, because it squats a Kubernetes in-tree group with a foreign kind.
* Bad, because it undercuts the README's claim of K8s-familiar conventions at the very first line
  an operator reads.

### Option C — `helvilette.io/v1` + `Cluster`

* Good, because it fixes the group, which is the most clearly wrong part.
* Bad, because `v1` promises compatibility the schema cannot keep while vault and probes are
  unimplemented.
* Bad, because it leaves `kind: Cluster` misnaming the object, and would force a second breaking
  change to correct it later.

## More Information

**API group survey.** Where projects put their own kinds:

| Project | Group | Owns the domain |
|---|---|---|
| k3s | `k3s.cattle.io`, `helm.cattle.io` | Rancher |
| Flux | `source.toolkit.fluxcd.io`, `kustomize.toolkit.fluxcd.io` | Flux |
| Argo CD | `argoproj.io` | Argo |
| cert-manager | `cert-manager.io` | Jetstack |
| Prometheus Operator | `monitoring.coreos.com` | CoreOS |
| Cluster API | `cluster.x-k8s.io` | Kubernetes SIG |

**Domain ownership caveat.** The convention asks for a domain the project controls. If
`helvilette.io` is not registered to this project, the strictly correct group would be a subdomain
of a domain that is. The practical risk is near zero, because Helvilette manifests are never
submitted to a Kubernetes API server and so cannot collide with a real CRD; the group functions as
a namespace label rather than a registered API surface.

**Follow-up work.** Strict unknown-key rejection (`yaml.Decoder.KnownFields(true)`) is the natural
completion of this decision, but it cannot land until `spec.vault` and `nodeGroups[].probes` have
types, since strict decoding would reject the shipped example manifests today. It should land with
the Vault / Secret Integration and Health Probes backlog items.
