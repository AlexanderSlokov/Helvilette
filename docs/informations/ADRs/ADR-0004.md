# Overlapping `nodeGroup` selectors are rejected at manifest load time

## Context and Problem Statement

When an agent's labels match more than one `nodeGroup`, `handleSync` in
`cmd/othela/server.go` dispatches only the first match and silently drops the
rest. The dropped groups are indistinguishable from groups that were never
declared.

The e2e manifest at `tests/e2e/data/playbooks/nginx-collection/helvilette.yml`
demonstrates the problem: two groups — `standard-proxies` and
`high-performance-proxies` — share the identical `nodeSelector: {role: edge-proxy}`.
Everything declared under `high-performance-proxies` (worker tuning, memory
limits, seccomp policy, a different vault secret) is dead configuration that has
never been applied. An operator reading the manifest would reasonably conclude
those settings are active. They are not, and nothing in any log contradicts that
belief.

Three approaches were considered:

1. **Reject overlapping selectors at load time.** Loudest and earliest. Consistent
   with how issue #13 was resolved (fail-fast on structural problems). Forces the
   operator to make the conflict explicit.
2. **Merge `extra_vars` across all matching groups.** Mirrors Ansible variable
   layering. But `vault-password-file` is a scalar, and the two groups in the e2e
   manifest name *different* vault secrets — merging has no correct answer for
   scalars that conflict.
3. **Keep first-match, log a WARN.** Cheapest and non-breaking, but leaves a
   surprising behaviour in place.

## Decision

**Option 1: reject manifests where two `nodeGroups` carry identical
`nodeSelector` maps.**

Rationale from the project owner:

> Two groups with conflicting configuration — different `extra_vars`, different
> `vault-password-file` — matching the same set of nodes is a specification error,
> not a feature. The operator must resolve the conflict, not Othela. Silent
> first-match dispatch hides a configuration conflict that the operator must
> resolve explicitly.

This is a breaking change for any manifest that declares overlapping groups.

### Scope of "overlap" for v1alpha1

For v1alpha1, "overlap" means **exact `nodeSelector` equality**: two groups
whose selector maps contain the same key-value pairs. True subset/superset
overlap (group A selects `{role: proxy}`, group B selects `{role: proxy, tier: hot}`)
is deferred. Computing whether two arbitrary selector sets can simultaneously
match a single label set requires enumerating the power set of possible labels
and is not yet needed — the observed defect in the e2e manifest is exact equality,
and that is the case this change must fix.

The `matches[0]` dispatch logic in `handleSync` remains for the subset edge case
but is now documented. Full subset-overlap rejection can land with the v1beta1
schema when selector semantics are finalized.

## Consequences

### Breaking

- Any manifest where two `nodeGroups` have identical `nodeSelector` maps is now
  rejected at load time with an error naming both groups and their shared
  selector.
- The e2e manifest must be updated: `high-performance-proxies` receives a
  distinct selector (e.g. adding `tier: high-performance`) to differentiate it
  from `standard-proxies`.

### Positive

- Configuration conflicts that were previously silent are now caught before
  any playbook is dispatched.
- The BACKLOG's "semantics decision" blocker for section 6.1 is resolved.
- Consistent with the fail-fast direction established by issue #13 and ADR-0002.

### Neutral

- Subset-overlap detection is deferred; a node carrying `{role: proxy, tier: hot}`
  can still match two groups with different selectors `{role: proxy}` and
  `{role: proxy, tier: hot}`. This is a known gap, not a regression.
