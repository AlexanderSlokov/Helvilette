# Fleet sync resolves the remote-tracking ref, and the fleet cache is disposable

## Context and Problem Statement

Issue #32 reported that a `helvilette.yml` pushed to the repository named by
`--fleet-repo` was never picked up. Othela had a poll loop — `StartFleetSync` in
`cmd/othela/server.go`, running on `--fleet-sync-interval` — so the loop was not
the missing piece. The defect was one layer down, in `pkg/git`.

`EnsureRepo` fetched and then called `repo.ResolveRevision("main")`. Two facts
about go-git combine badly here:

1. A clone stores the refspec `+refs/heads/*:refs/remotes/origin/*`, so a fetch
   advances `refs/remotes/origin/main` and nothing else. `refs/heads/main` stays
   at the commit the clone landed on.
2. `ResolveRevision` expands a bare name through `plumbing.RefRevParseRules`,
   which tries `refs/heads/%s` **before** `refs/remotes/%s`. The bare name `main`
   therefore matched the stale local branch every time.

Othela polled on schedule, checked out its clone-time commit on every tick, and
reported success. Nothing in any log contradicted the belief that GitOps was
working. `pkg/git` had no tests, which is why this survived the e2e suite: the
suite only ever asserts the state after the first clone.

The same code path is used by the Agent when it materialises a job's repository,
so a job pinned to a branch ran whatever that branch pointed at when the Agent
first saw it.

Three approaches were considered:

1. **Resolve `refs/remotes/origin/<ref>` explicitly, then hard-reset.** Says what
   it means, independent of go-git's expansion order.
2. **Keep `ResolveRevision`, but pass a fully-qualified ref.** Callers would have
   to know to write `refs/remotes/origin/main` instead of `main`, pushing a
   go-git implementation detail out into the `--fleet-branch` flag.
3. **Delete and re-clone on every poll.** Always correct, but it re-downloads the
   whole repository once a minute for every Othela in the fleet.

## Decision

**Option 1.** `pkg/git.EnsureRepo` resolves a ref in this order, never consulting
local branches:

1. `refs/remotes/origin/<ref>`
2. `refs/tags/<ref>`
3. `<ref>` as a commit SHA already present in the repository

An empty ref means the branch the clone landed on, read from local `HEAD`: a full
clone does not create `refs/remotes/origin/HEAD`, so `HEAD` is the only record of
what the remote handed us. A ref that matches none of the three is an error
naming the ref and the references that were tried.

### The fleet cache is a derived artifact

`EnsureRepo` converges the worktree with `git reset --hard` rather than `pull`.
This follows from what the directory is: `--state-dir/fleet` is a cache Othela
owns and nobody edits. A merge conflict there is not a situation to resolve, it
is a situation that must not arise. A hard reset also moves the local branch,
which keeps `HEAD` attached from one poll to the next instead of leaving a
detached HEAD behind.

For the same reason, a cache directory that exists but will not open as a
repository — a half-finished clone — is deleted and cloned again. A *fetch*
failure does not trigger this: a network outage must leave the existing checkout
intact, because serving yesterday's manifests beats serving none.

### `EnsureRepo` returns the resolved commit SHA

The caller needs to distinguish a poll that changed something from one that did
not, and an operator needs to know which commit is live. The SHA is returned as
a hex string rather than a `plumbing.Hash`, so go-git stays inside `pkg/git`.

Othela logs at `info` when the SHA moves (`fleet_commit`, `previous_commit`,
`playbook_count`) and at `debug` when it does not. Before this, a successful sync
logged at `debug` only, so at the default log level a working poll loop and a
dead one looked identical.

### Polling only; no webhook for v1alpha1

Issue #32 asked for polling *or* a webhook receiver. A webhook is an
unauthenticated write endpoint on the control plane and needs its own
authentication decision (shared secret, HMAC over the payload, source-IP
allowlisting) before it can exist. That decision is deferred. `--fleet-sync-interval`
defaults to one minute, which bounds propagation delay at a cost the control
plane can carry.

## Consequences

### Positive

- A commit pushed to the fleet repository is picked up within one
  `--fleet-sync-interval`. This is what issue #32 asked for.
- A file deleted upstream disappears from the cache, so a retired playbook stops
  being dispatched.
- The live commit SHA appears in Othela's logs and in the Agent's job logs, so
  "which code ran" is answerable after the fact.
- A half-finished clone self-heals instead of failing on every poll forever.
- `pkg/git` has tests, including one that fails against the previous
  implementation (`TestEnsureRepo_PicksUpCommitsPushedAfterClone`).

### Breaking

- `EnsureRepo` returns `(string, error)` instead of `error`. Both call sites —
  `cmd/othela/server.go` and `cmd/agent/main.go` — are updated.
- `StartFleetSync` takes a `context.Context` and a `FleetSyncConfig` instead of
  four positional arguments. Cancelling the context stops the loop; previously
  the goroutine had no exit and outlived graceful shutdown.
- Local modifications inside `--state-dir/fleet` are discarded on every poll.
  This was already true in intent and is now true in fact.

### Neutral

- A hard reset does not remove untracked files, matching `git reset --hard`.
  Untracked leftovers in the cache are inert: the loader only reads
  `helvilette.yml` files, and one left behind by a previous commit would be
  loaded. Removing them needs `git clean`, deferred until it is observed to
  matter.
- Resolution is hardcoded to the `origin` remote. Othela creates the clone, so no
  other remote exists.
