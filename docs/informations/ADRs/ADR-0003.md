# Playbooks are pulled artifacts, not a mounted directory: `--data-dir` splits into `--playbook-dir` and `--state-dir`

## Context and Problem Statement

`cmd/othela/main.go` gave a single flag two contradictory jobs:

```go
dbPath := filepath.Join(dataDir, "server", "db", "state.db")  // written
loader, err := playbook.NewLoader(dataDir)                    // read
```

Playbooks are read-only input supplied by the operator. The SQLite store is read-write state
owned by Othela. Both lived under `--data-dir`, so the writable database sat *inside* the
directory of read-only input, at `{data-dir}/server/db/state.db`.

In the e2e stack that directory is `tests/e2e/data/playbooks`, bind-mounted from inside the Go
module tree. Two distinct defects followed from the same cause.

**The module tree acquired root-owned files.** Othela ran as root in its container, so through
the bind mount the host ended up with `tests/e2e/data/playbooks/server` owned by `root:root`
mode 750. Because the path is inside the module tree, package listing failed before any code
was compiled:

```
$ go vet ./...
pattern ./...: open tests/e2e/data/playbooks/server: permission denied
```

That is the exact command CI runs. CI stayed green only because a fresh checkout never has the
directory — it is created by running the stack locally.
[#17](https://github.com/AlexanderSlokov/Helvilette/issues/17) patched this by running the
compose container as the host UID, which fixed one of the two paths that start Othela and left
`tests/e2e/gitops_test.go` — which builds containers with testcontainers and never sets `User`
— still recreating the directory as root.

**The same playbook had two sources of truth.** BACKLOG 6.3 records that the e2e git-server
serves the *committed* manifest while Othela reads the *working tree*. Editing
`helvilette.yml` without committing therefore changes what Othela dispatches but not what the
agent clones, and the two silently disagree.

Both defects are symptoms of treating a mutable local directory as if it were a versioned
artifact.

## Decision Drivers

* **Operator Experience from day-0 to day-n is the overriding priority for the naughtian
  stack.** A control plane whose behaviour depends on the uncommitted state of a working tree
  cannot be reasoned about during an incident.
* Consistency with the agent, which already resolves playbooks by reference and caches them
  ([BACKLOG 3.1](../../../BACKLOG.md)).
* Not writing into a source tree, which is what made a permissions detail escalate into broken
  Go tooling.
* Readiness for systemd packaging (BACKLOG 3.5), which needs a conventional writable state path.
* Compatibility risk, bounded because the project is pre-release at v0.1.0.

## Considered Options

* **Option A — split into `--playbook-dir` (read-only) and `--state-dir` (writable), remove
  `--data-dir`.**
* **Option B — keep `--data-dir`, move only the database** to a separate writable path.
* **Option C — keep the layout, standardise container UIDs everywhere**, including the
  testcontainers path missed by #17.

## Decision Outcome

Chosen option: **"Option A"**, because it removes the class of defect rather than each
instance, and because it brings Othela into line with the model the agent already follows.

**On the artifact model.** A playbook is an immutable artifact identified by
`(repo, playbookPath, commit SHA)`. The commit SHA is its digest. This is already how the
agent works after BACKLOG 3.1: the `Job` carries a reference rather than `PlaybookContent`, and
`pkg/git/cache.go` pulls it into a local cache. Othela is the component that had not caught up,
still reading playbooks as a live local directory. The mapping that decided it:

| Docker | Helvilette |
|---|---|
| `nginx:1.25` | `(repo, playbookPath, version)` in `Job` |
| digest `sha256:...` | commit SHA |
| registry | Git remote |
| `/var/lib/docker` content cache | agent git cache (`pkg/git/cache.go`) |
| container and volume state | Othela SQLite, agent workspace |
| `docker build` from a local context | local playbook directory, development only |

Under this model a local playbook directory is the equivalent of `docker build` against a
working tree: legitimate for development, wrong as the way a control plane resolves what to
deploy. It is therefore demoted to an explicit development override, mounted read-only, rather
than being the primary input path.

**On where state goes.** Portainer is the closest available prior art and was inspected
directly rather than recalled. Its container mounts one data directory, and everything it owns
lives inside it:

```
portainer_data/
├── portainer.db      root:root  600     BoltDB
├── compose/          root:root  700     user stack definitions
├── custom_templates/ root:root  700
└── chisel/           root:root  700
```

The instructive part is that Portainer makes **no** attempt to match the host UID. Its entire
data directory is root-owned at mode 600/700 and this bothers nobody, because the directory
sits outside any source tree. What matters is where the writable path points, not which UID
writes to it. Option C — standardising UIDs — would have made the symptom rarer while leaving
a writable bind mount inside the module tree, so any container that ever ran as root would
reintroduce it.

Portainer also does not ask users to bind-mount their compose files in. It fetches stacks from
Git or upload and keeps its own copy under `compose/`. That is the same ownership boundary this
decision draws: the system owns its copy of the artifact.

**On the flag names and defaults.** `--state-dir` defaults to `/var/lib/helvilette/othela`,
following the FHS convention for variable state that systemd unit files will need in BACKLOG
3.5, and mirroring k3s, which keeps its SQLite store at
`/var/lib/rancher/k3s/server/db/state.db`. The database lands at `{state-dir}/db/state.db`.
`--playbook-dir` names what it actually holds. The previous default,
`helvillette/othela/data/playbooks`, also carried a misspelling of the project name that is
corrected in the same breaking change rather than being preserved for its own sake.

**On removing `--data-dir` outright.** A deprecated alias was considered and rejected. An alias
keeps a name working while silently changing what it means: `--data-dir` currently designates
the playbook directory and happens to also receive state, so mapping it onto either new flag
would be wrong half the time. A removed flag produces an immediate, self-explanatory error; an
alias produces a working command with different behaviour. The project is pre-release, and
CHANGELOG already carries BREAKING precedent from the manifest schema change in
[ADR-0002](ADR-0002.md).

### Consequences

* Good, because no writable path is bind-mounted into the Go module tree any more, so the
  broken-`go vet` failure cannot recur through either the compose or the testcontainers path.
* Good, because Othela and the agent now describe playbooks the same way, which is a
  precondition for the reconciliation loop in BACKLOG 3.6 to compare like with like.
* Good, because `--state-dir` gives systemd packaging (BACKLOG 3.5) a conventional path with no
  further change.
* Good, because BACKLOG 6.3 is resolved at its cause rather than documented as a caveat.
* Bad, because it is a breaking change: every invocation passing `--data-dir` fails until it is
  updated. Mitigated by the error naming both replacement flags.
* Bad, because the default `--state-dir` is not writable by an unprivileged user, so
  `make run-othela` without arguments falls back to in-memory storage. The existing fallback
  already warns loudly, and the Makefile passes an explicit path.
* Neutral, because Othela still reads playbooks from a directory in the e2e stack. Resolving
  them by Git reference on the Othela side is a larger change, tracked separately; this decision
  fixes the ownership and mutability boundary that made the directory dangerous.

### Confirmation

* `cmd/othela/main_test.go` covers the flag surface: `--data-dir` is rejected with a message
  naming both replacements, and the database path derives from `--state-dir`.
* The e2e suite asserts the stack still reconciles with playbooks mounted read-only.
* `go vet ./...` and `go list ./...` are expected to succeed after a full e2e run on a clean
  tree, which is the regression this decision exists to prevent. Before the change they failed
  with `permission denied`.

## Pros and Cons of the Options

### Option A — split the flags, remove `--data-dir` (chosen)

* Good, because it removes the read/write conflation that caused both defects.
* Good, because it matches how the agent already treats playbooks.
* Good, because it gives systemd a conventional state path for free.
* Bad, because it breaks every existing invocation and every deployment script.

### Option B — keep `--data-dir`, move only the database

* Good, because it is a small change and fixes the permission symptom.
* Bad, because playbooks remain a mutable directory, so BACKLOG 6.3's two-sources-of-truth
  defect survives untouched.
* Bad, because `--data-dir` would keep a name that no longer describes what it holds.

### Option C — standardise container UIDs everywhere

* Good, because it requires no flag change and no compatibility cost.
* Bad, because it treats the symptom: a writable bind mount stays inside the module tree, so
  any container that runs as root reintroduces the failure. #17 demonstrated exactly this by
  fixing one of two paths.
* Bad, because it leaves the artifact model inconsistent between Othela and the agent.

## More Information

**Why UID matching is the wrong lever.** The failure needs three things at once: a writable
path, a container UID that differs from the host user, and the path being inside the module
tree. Option C removes the second. This decision removes the first and third, which is why it
holds even for a container that runs as root.

**Related e2e fragility, fixed alongside but not by this decision.** The git container ran
`apk add --no-cache git git-daemon` at startup while the suite waited on
`wait.ForLog("Ready to rumble")`, so every run depended on a package download finishing inside
the default startup deadline. It was observed failing once under load and passing on an idle
host. Git is now baked into the image. This is unrelated to the directory layout and is
recorded here only because both were found in the same investigation.
